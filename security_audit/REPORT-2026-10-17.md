# Follow-up security audit

**Review period: 2026-10-17 to 2026-10-18. Baseline: `f03e41d` (branch `production-readiness`, after the October remediation and the production-readiness work). Fixes: commits `c3bacbf` to `401cb61` on the same branch.**

The first audit ([REPORT.md](REPORT.md), F01–F34) was followed by about twenty commits that added schema migrations, operator commands, a request log, a Redis-outage fallback, error pages, Helm backups and a release pipeline. This review covered the whole code base again, with particular attention to that new code and to whether the earlier fixes still hold.

**Result:** no critical or high-severity issue. Four medium-severity issues (two in the release pipeline, one in Redis-outage handling, one in the Docker Compose deployment) and thirty-one low-severity issues were found and fixed, with regression tests, except where noted below. Twelve informational items were fixed as hardening; seven are recorded as accepted. Some decisions remain with the repository owner and the operators (section [Owner actions](#owner-actions-and-residual-risks)).

## Method

Seven independent reviews ran in parallel, each with its own scope and disposable environment:

| Review | Scope |
| --- | --- |
| Identity and sessions | OAuth flow, local sign-in, JWT sessions, cookies, CSRF, logout and account deletion. |
| Authorization and data | Object and function authorization, token lifecycle, validation API, administration API, last-administrator rule, concurrency (PostgreSQL and SQLite race tests). |
| HTTP pipeline and front end | Middleware order and coverage, admission and rate limiting (including hung, refused and full Redis), body limits, logging, security headers, templates and scripts. |
| Database and operations | SQL, production role check, migration runner and adoption, configuration loading and validation, operator CLI, time handling, runbooks. |
| Containers and deployment | Dockerfiles, entrypoint, Helm chart (rendered and installed on a k3s cluster with Pod Security "restricted" and enforced NetworkPolicies), PostgreSQL and Redis hardening, backup job, Docker Compose. |
| CI/CD and supply chain | Workflows (triggers, permissions, injection, caches, pinning), release integrity, dependencies, base images, risk gate, Dependabot, documentation build, secrets in the git history. |
| Dynamic testing | The running application attacked over HTTP as an anonymous client, a malicious site, a signed-in user and a holder of stolen credentials. |

Every reported finding was reproduced or confirmed by reading the code path before it was fixed; claimed issues that a defence elsewhere neutralises were dropped. Two reviews ended early; their remaining checks were covered by the other reviews, the regression suite and re-runs of their test scripts.

Tools: Bandit 1.8.6, Semgrep 1.181.0, pip-audit 2.10.1, Trivy 0.70.0 and 0.76.0, Grype 0.120.1, Syft, gitleaks 8.30.1, trufflehog 3.99.2, zizmor 1.31.1, actionlint 1.7.12 (with shellcheck), kubeconform, helm lint. Testing used synthetic keys, disposable PostgreSQL 16 and Redis containers, a synthetic Compose stack in production mode, a disposable k3s cluster and a local registry. No production system was accessed.

## Findings and fixes

Severity describes the condition found, with its preconditions. "Fixed" means the code, templates or documentation changed and a test or rehearsal confirms it; existing installations get the fixes with the next deployment.

### Availability

| ID / severity | Finding | Fix and verification |

| F54 — Low | Per-address keys let a client with many addresses (one IPv6 /64 suffices) fill the 64 MB Redis; a full Redis refused writes, which blocks password sign-in (by design, fail closed), while `/readyz` still reported Redis as "ok". | IPv6 clients are counted per /64; readiness writes a counter instead of pinging. ### Informational

Fixed as hardening: repeated revocation overwrote the first revocation time; renewal without a body failed after a rotation; the administration token API paged without a tie-breaker and the users list showed an empty last page; trailing-slash redirects were built from the `Host` header; responses lacked `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy` and `Permissions-Policy`; a shown token could survive in the back-forward cache; `--password-stdin` echoed a password typed at a terminal; the runbook set database passwords in SQL text; revocations were purged without allowing for clock skew between replicas; the server header and a short keep-alive (sporadic 502s behind ingress-nginx); setuid binaries and a world-writable file in the image; unknown top-level chart values were ignored.

Accepted, with reasons:

- The validation API distinguishes an expired token from an unknown or revoked one. Gateways use it to tell users to renew; it requires possession of the token.
- The administrator session lifetime is enforced when the session is issued, not when it is checked; changing it needs the signing key, and every promotion ends existing sessions.
- `/readyz` is public and reports whether Redis is degraded; restrict it at the ingress if that matters.
- Checksum annotations hash chart-supplied passwords (an offline guessing oracle for readers of pod metadata); use `existingSecret`, as production documentation requires, and random passwords.
- API-token and deletion-record hashes share one key; they cannot collide because token prefixes cannot contain the separator used for the other purposes.
- The documentation site loads Mermaid from unpkg without an integrity hash (documentation only).
- `HEAD` on pages answers 405; development-mode cookies have no `__Host-` prefix (production refuses that mode's settings).

## Owner actions and residual risks

1. **Repository settings for the release path:** required reviewers for the `release` environment and the JSC registry secrets moved into it; branch protection for `main` (pull requests, passing CI); a tag ruleset restricting `v*` tags to release managers; organisation-wide two-factor authentication; fewer owners; immutable releases; consider CodeQL. The workflow checks (F36) do not replace these.
2. **Container risk assessments** for the application image (44 Debian findings in privileged utilities the service never runs) expire on 2026-11-10; CI fails afterwards by design. Review them with a fresh scan.
3. **Redis capacity:** password sign-in fails closed when Redis is down or full (by design); size Redis memory and edge protection for floods from many real addresses.
4. **Rollback across releases:** a release refuses a schema migrated by a newer one; there is no marker of backward compatibility between revisions, so rolling back after a migration means rolling forward or restoring.
5. **Email verification:** no `email_verified` flag is stored; administrators identify OAuth accounts by subject.
6. **Datastore images:** Grype reports a low-severity Redis finding (CVE-2025-49112) and a medium BusyBox finding (CVE-2025-60876) with no fixes available; both are below the gate and tracked by the scans.
7. **Environment evidence** listed in the first report (identity provider policy, enforced network policies, certificates, backups off the cluster, monitoring, restore rehearsal, load test) still applies; the [production checklist](../docs/deployment/checklist.md) lists it.

## Verification

- **Tests:** the regression suite passes on SQLite and on PostgreSQL 16, including the new tests in `tests/test_followup_audit.py` and `tests/test_migrations.py` (role check, adoption, lock behaviour, newer schemas, schema comparison) and the race tests of the authorization review.
- **Chart:** render tests (now including names and labels for long release names, the backup script and the PostgreSQL access rules), `helm lint --strict`, kubeconform against Kubernetes 1.31.
- **Workflows:** actionlint and zizmor report no findings (zizmor's auditor persona only style notes); every inline script parses; the release build and publish steps were rehearsed against a local registry, including refusal of an existing version.
- **Images:** Trivy 0.76.0: application image 44 high findings, all covered by the current assessments; PostgreSQL and Redis images no findings. Grype on the datastore images: no high or critical findings. No setuid or setgid files in the application image.
- **Dependencies:** pip-audit finds no known vulnerabilities in the production dependencies or in any dependency group. gitleaks and trufflehog find no secrets in the history (all matches are placeholders, test values or digests).
- **End to end:** the synthetic Compose stack in production mode (verified TLS, restricted runtime role, Redis 8 with the narrowed ACL) passed readiness with the Redis write probe, honoured forwarded client addresses, isolated the datastores from the internet, refused the PostgreSQL administrator over the network, created an administrator with the CLI, signed in, created and validated a token, answered NUL input with 422, and took a backup with the new job script.
