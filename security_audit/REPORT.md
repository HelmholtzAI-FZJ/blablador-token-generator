# Production security audit and implemented remediation

**Review period: 2026-10-11 to 2026-10-12. Baseline: `3341bc087ffbf4f76b469cd7f272dfbeafdcebe3`. Remediation is in the current working tree.**

The review found real authorization, revocation, concurrency, availability and deployment weaknesses. They have been corrected in application code, deployment templates and tests. This is an implementation report, with the original evidence preserved separately. No production service was attacked, changed, deployed or restarted, and no production database was migrated. A successful local test is not evidence that an unseen production ingress, identity provider or cluster is correctly configured.

The application now rejects unsafe production settings, uses durable session revocation and atomic session epochs, preserves administrator decisions across OAuth logins, serializes account/token mutations, prevents administrator lockout, separates OAuth restoration from local account creation, and supports explicit credential rotation and incident containment. Admission checks precede authentication and body parsing; password/counter work runs outside the event loop. Deployment changes enforce TLS, constrained datastore identities, network isolation, secret references, runtime hardening and reviewed image identifiers.

## Method and coverage

The review traced every route, browser action, authentication path, database model, deletion/restoration path, configuration field and production deployment template. Independent reviews covered authentication, API/data invariants, and infrastructure; integration review challenged their fixes and found additional races and admission/error-path gaps. Scope included application Python, Jinja templates, all three browser scripts, cookies, dependency metadata/lockfile, Docker builds, Compose, Helm templates/schema/helpers/init scripts, startup scripts, CI and dependency update configuration. Existing design documents were checked for stale security claims and current operating guidance was replaced.

Testing used synthetic keys/profiles, throwaway SQLite databases and disposable PostgreSQL/Redis containers. PostgreSQL ports bound only to loopback on ephemeral ports; runtime transport tests used synthetic CAs. Own test containers were removed. Images were built and scanned locally; there was no registry publication. The real ignored local configuration was inspected only for non-secret security settings and file metadata; secret values were not copied into this audit. Local `config.yaml` and `cookies.txt` permissions were tightened to `0600`.

Source inspection and tests covered authentication bypass, token ownership, administrative authorization, stored/DOM XSS, CSRF, OAuth state/PKCE, credential leakage, malformed input, database rollback, concurrent revocation/quota/membership changes, deletion races, asynchronous blocking, request admission, TLS, runtime privilege, secret rollout and supply chain. Scanner findings were reviewed rather than equated with remotely exploitable application flaws. The audit did not perform internet-scale load testing, kernel/container-escape testing, penetration testing of the live IdP, or validation of unseen production infrastructure.

## Finding register and completed fixes

Severity describes the original condition and its stated preconditions. **Fixed** means code/templates/tests were changed; it does not mean an existing installation has received them. Configuration and operational findings remain relevant until the deployed configuration and upgrade steps have been verified.

### Identity, sessions and authorization

| ID / original severity | Original evidence and consequence | Implemented change and verification |
| --- | --- | --- |
| F01 — High, conditional | Long public `REPLACE_WITH_…` example signing/HMAC keys passed the length-only guard. Deploying those values would expose known session signing material. | Examples contain empty required secrets; known/default/placeholder prefixes and all-whitespace values are rejected after normalized checks. Keys must be distinct and at least 32 characters. Unknown configuration fields and input-bearing error representations are rejected/hidden. Config regression cases cover these checks. |
| F02 — High | A configured OAuth admin demoted in the database became admin again on the next login. Config promotion could also elevate an existing session without changing its epoch. | Bootstrap grants apply only to newly created OAuth accounts. Existing roles are authoritative database decisions; actual role changes invalidate prior sessions. Tests demonstrate stable demotion and no retroactive elevation. |
| F03 — Medium; high during stolen-session containment | Injected revocation commit failure still produced successful logout, while the session remained usable. The browser also redirected regardless of HTTP success. | Logout succeeds only after durable `jti` revocation; storage errors return sanitized `503`. The browser stays on the page and reports failure. Idempotent logout and replay rejection are tested. |
| F04 — Medium | Two stale ORM instances both incremented epoch `0` to `1`; a session issued between security changes could survive the second change. | SQL performs `session_epoch = session_epoch + 1 RETURNING session_epoch`; the ORM value is updated without a second stale write. Concurrent security-change tests prove distinct increments and invalidation. |
| F05 — Medium | The only admin could self-delete. Concurrent demotions/deletions could each pass a stale admin count and remove all admins. | PostgreSQL transaction advisory membership lock and account row locks serialize membership mutations. Self-deletion shares the guard. Tombstoned rows do not count as usable admins; bounded checks fail closed if availability cannot be established. SQLite uses `BEGIN IMMEDIATE` for development parity. |
| F06 — Medium | A pending request authenticated before waiting for an owner/admin lock could mint credentials after a revoke-all transaction invalidated its session. | Real cookie-authenticated mutations recheck the session's `jti`, epoch and live account after locking, against refreshed state. Tests reject stale pending owner/admin writes after containment. |
| F07 — Medium, conditional | Local account creation removed OAuth deletion records sharing an email, allowing a disabled provider subject with an unverified email to return. | Local provisioning lifts only local-email tombstones. OAuth restoration requires the explicit admin subject endpoint. Tests preserve unrelated OAuth tombstones and check restoration scope. |
| F08 — Medium, conditional race | OAuth creation could race deletion; a newly persisted row could outlive the first tombstone check. | OAuth checks deletion before and after persistence/reload; browser and API authentication also reject tombstoned identities. Raced rows fail closed and emit a cleanup event rather than issuing a session. Last-admin protection excludes these disabled rows. |
| F09 — Credential-policy gap | Newly provisioned/reset local passwords accepted short common composition-pattern passwords. Only per-IP attempts were limited; administrator sessions lasted as long as ordinary sessions. | New/reset passwords require 15 characters, a configurable common-password blocklist and at most 72 UTF-8 bytes. Shared HMAC-normalized account throttling supplements IP limits. Admin JWT lifetime defaults to one hour and cannot exceed the regular lifetime. Legacy password verification remains compatible. |
| F10 — Containment/lifecycle gap | Password reset revoked browser sessions but there was no single operation to contain all API credentials and sessions. Renewal reused the old credential. | Self `POST /tokens/revoke-all`, admin `POST /api/admin/users/{id}/revoke-credentials`, and owner `POST /tokens/{id}/rotate` are implemented, audited and exposed in the UI. Rotation replaces the digest and invalidates the old value; renewal retains its documented lifetime-extension semantics. |
| F11 — Provider-input hardening | Provider HTTP calls lacked an explicit overall response bound and strict bounded profile/token types; malformed responses could cause unsafe errors or excessive work. | Fixed HTTPS endpoints, no redirects, a total timeout, bounded streamed bytes, identity-only encoding, strict token/profile types and sanitized provider errors. Tests cover oversized/malformed responses, type confusion, failure and timeout. |

Legacy compatibility remains explicit: existing shorter local passwords still verify, and legacy API tokens with NULL expiry remain valid until revoked. Newly created, renewed or rotated tokens receive bounded expiry. Inventory legacy credentials and retire/reissue them under the approved rollout plan; this audit did not inspect or alter real credential rows.

OAuth is a fixed-provider authorization-code plus HTTPS UserInfo flow. It does not validate an ID token or implement a full OIDC relying-party claim-validation pipeline. No unauthenticated token-substitution bypass was demonstrated against an honest fixed provider with state and PKCE. This limitation and issuer migration requirements are documented in the threat model; a missing nonce was not falsely classified as a standalone exploit. Administrator MFA, provider subject guarantees and IdP offboarding remain external integration requirements.

### Input, persistence and resource use

| ID / original severity | Original evidence and consequence | Implemented change and verification |
| --- | --- | --- |
| F12 — Medium | With quota `1`, concurrent token creations produced two rows. | Token mutations lock the owner before count/write; four concurrent creations yield exactly one success. Verified on SQLite and PostgreSQL. |
| F13 — Medium | Authentication dependencies performed database rejection before route limits. A revoked session could repeatedly trigger expensive rejection without `429`. | Shared per-IP admission runs before body parsing/authentication; concurrency is bounded. Invalid sessions cannot bypass this layer. Gateway exemptions are exact-path and bounded-network exceptions; `/0` exemptions are rejected. |
| F14 — Medium | Synchronous bcrypt and Redis counter calls blocked the async event loop. A ten-millisecond timer waited approximately 168 ms during the bcrypt probe; default storage timeouts amplified stalls. | Password operations run in threads under cancellation-safe capacity accounting. Counter checks run in threads with bounded connection/read timeouts. Shared local-account counters do not inherit SlowAPI's memory fallback. Tests verify loop progress and capacity behavior. |
| F15 — Availability gap | Body size was bounded but slow uploads and concurrent admission were not; readiness bypassed resource limits during initial remediation. | Body deadline defaults to 10 seconds, size to 64 KiB, concurrent admitted requests to 128 per worker. Readiness is admitted and bounded. GET liveness is a constant response before body/storage work; other methods are admitted normally. |
| F16 — Medium availability | Every valid token check wrote/committed the same usage row. A best-effort write rollback expired ORM attributes and produced `MissingGreenlet`/500 instead of the already computed valid response. | Usage writes coalesce to a configurable interval (default 60 seconds), use conditional monotonic updates and preserve a primitive response before rollback. Tests inject failure and validate correct response behavior. |
| F17 — Low robustness | Valid extreme timezone datetimes could overflow normalization; enormous page numbers overflowed database offsets. | Typed datetime normalization catches overflow, expiration is future/bounded, conflicting expiration inputs are rejected, and pagination has numeric bounds. Edge tests return client errors rather than server faults. |
| F18 — Low secret hygiene | Pydantic request errors echoed passwords supplied in invalid requests. Unexpected exceptions could be logged by the server with original messages. | Validation responses retain only location/type/message, excluding input/context. Configuration hides input in errors. ASGI error safety returns generic failures and suppresses original exception messages before server traceback handling; interrupted streams raise only a sanitized exception. |
| F19 — Low header consistency | Direct `413` and unexpected `500` paths missed security/cache headers. Authentication API errors could redirect rather than return an API error. | Outer security-header middleware covers admission/body/normal responses; safe generic error handling covers faults. API/unsafe unauthenticated requests return `401`; browser navigation uses `303`. HTTP exception headers are preserved. |
| F20 — Scale/operability gap | Owner queries lacked an index in existing databases, and bulk purge loaded revoked rows into application memory. | New databases create `ix_tokens_user_id`; an explicit idempotent existing-database migration builds it `CONCURRENTLY` on PostgreSQL and rejects incompatible/invalid definitions. Purge uses bulk SQL. Existing databases require the documented migration; startup `create_all` does not pretend to alter them. |
| F21 — Audit/diagnostic gap | Some provider/logout/revocation failure events were absent or unsafe. Setting a high general log level could suppress security audit INFO events. | Sanitized lifecycle/failure events were added; audit/account INFO remains enabled independently of higher general logging thresholds. Internal IDs and error types are used for sensitive failure paths. Existing email-bearing administration/account events are documented as PII. |

The body deadline begins after the HTTP server has parsed headers. Edge header/connection/TLS limits are therefore still part of the production ingress requirements. The gateway exemption increases validation capacity, but does not remove the per-worker concurrency bound or database authorization checks. Database authorization failures fail closed; optional usage telemetry is the specifically permitted best-effort operation.

## Verification results and interpretation

Baseline SQLite: **92 tests passed**, 78% statement coverage. Final SQLite: **207 passed, two PostgreSQL integration tests skipped**, 83% statement coverage; final PostgreSQL: **209 passed**. The remediated suite adds meaningful negative-path, race, middleware, provider, migration and containment tests; raw results and coverage are saved under `evidence/final-*`. Warnings include existing naive-UTC deprecations and the Starlette test-client compatibility warning; they are recorded rather than hidden.

The PostgreSQL behavior suite runs with an intentionally powerful synthetic test role. It proves query, lock, race and migration behavior, **not** least privilege. Its additional privilege integration test creates a separate restricted role in the disposable instance, accepts schema/database ownership and monitoring grants, and rejects each unsafe attribute, server-file/program role, inherited privileged role and a privileged login hidden by `SET ROLE`. This startup check is a connection-time policy, not continuous monitoring of operator grant changes. Separate fresh-role TLS/runtime tests prove the constrained production role. The application image smoke test uses synthetic development transport settings inside the production image to exercise the packaged application without any live IdP/store; it does **not** prove the real production transport configuration. Every packaged application source hash matches the reviewed workspace. These distinctions prevent unrelated passing checks from overstating assurance.

Production dependencies were audited against the hash-locked export: 38 packages, no reported known vulnerabilities or skipped packages at the recorded scan time. Installed-environment inventory is also preserved. Final Bandit results contain the intentional all-interface application configuration default used inside isolated containers; it is not evidence of exposed production ingress. Full container scans include all severities and must be read with the reachability assessments below.

Local git inspection covered 116 reachable commits and sensitive filename reachability; no referenced `config.yaml`, cookie jar, `.env`, key/certificate filename, `refs/original` backup or unreachable local object was found. Current source secret-pattern review and image secret scanning found no newly embedded production secret. This is not a claim of exhaustive historical content entropy detection, nor proof that an unreferenced GitHub object is gone. The earlier report's claim about old remote OAuth credentials/rotation could not be independently verified from local objects; treat incident credential rotation and remote deletion as an external recorded-history requirement.

## Residual image risk and release gate

The initial application image had 172 scanner entries, including six base-pip issues and 44 HIGH Debian package matches across eight distinct CVEs. The runtime installers and every available package fix identified by the inspected scan have been addressed. Some Debian findings have no published fixed version for the pinned release; they remain visible in the full inventory.

The eight HIGH CVEs relate to privileged mount/namespace/ACL paths, `infocmp`, systemd-homed and Perl Archive::Tar. Image inspection verified absent homed/Archive::Tar features; source review found no application invocation of the installed mount/namespace/terminfo utilities. The enforced non-root, capability-free, no-privilege-escalation, read-only workload removes the described privileged paths. These are **workload non-affected assessments**, not claims that the underlying packages were patched or that arbitrary interactive use of the image is safe. Exact package/version assessments expire on **2026-11-10**; changed versions, new HIGH/CRITICAL findings or expired assessments fail CI. Removing these protections or adding a subprocess/archive/terminal feature invalidates the relevant assessment immediately. Vendor references and all lower-severity findings remain in the inventory.

The local scan architecture is Linux arm64. Deploying amd64 or a different digest requires that image's CI scan, runtime checks and final manifest identity; local image IDs must not be substituted for registry manifest digests.

The final hardened PostgreSQL and Redis scans report **zero vulnerability entries across all severities**, after removing the unused Go helper and applying available signed OpenSSL/zlib fixes. The final application inventory and local identities are recorded in the container inventory and raw evidence. These scan results describe known advisories and their recorded database freshness, not proof that the images contain no undiscovered vulnerabilities.

## Production acceptance requirements outside this checkout

Application defects and reproducible unsafe deployment defaults were fixed here. The following require actual environment evidence before production acceptance:

1. **Release identity:** publish the built images through the authorized release workflow, scan the target architecture/digests, record provenance/SBOM and deploy the reviewed registry manifest digests. No image was pushed by this audit.
2. **Upgrade and identity:** migrate an existing runtime superuser to the constrained role, apply the owner index migration, verify current admins and bootstrap rules, and exercise login/state/PKCE/subject/email policy with the real confidential client.
3. **Network and TLS:** verify public HTTPS and redirects, forwarded-header integrity, inability to reach the app from untrusted pods, enforced ingress/egress selectors, datastore certificate SAN/CA trust and rejection of plaintext/unauthenticated connections. Provisioned certificates and cluster peer identities are not repository data.
4. **Identity assurance/lifecycle:** enforce administrator MFA and the required login assurance at the IdP or access layer; implement and test the organization's offboarding trigger to the explicit containment/deletion operations. Upstream logout or disable does not automatically revoke independently issued API credentials.
5. **Secret and incident recovery:** protect and back up signing/HMAC keys, coordinate worker/replica rotation, redact callback query strings and authorization/cookie/body data in every edge/access logger, and test credential/cache containment. A HMAC key change cannot reconstruct historical tombstones from anonymous hashes.
6. **Availability and persistence:** select acceptable datastore HA and backup objectives, test restore without re-enabling revoked/deleted identities, verify storage encryption, tune NAT/gateway budgets and edge connection/header limits, and test representative load/failures. Bundled single datastore replicas are not HA.
7. **Privacy and monitoring:** approve retention of pseudonymous tombstones, profile data, email-bearing audit events and backups; protect centralized logs; alert on containment failures, repeated login failure, bootstrap/restore/admin changes, readiness failures and stale image-risk assessments.

These are concrete deployment/integration gates rather than concealed application fixes. Their live-environment evidence is absent from this workspace, so this report does not assert that an unseen deployment is ready for production.
